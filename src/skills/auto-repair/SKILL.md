# 自动化闭环测试与修复（Auto Repair Loop）

对仓库执行"测试 → 修复 → 回归"闭环，直到所有已知 Bug 被测试证明修复，或达到迭代上限。**一切决策以实际测试结果为准，禁止凭主观判断替代测试证据。**

## 状态机

```
INIT → SCAN → PATCH → VERIFY → REGRESS → DONE
                 ↑________|       ↑_______|
                 未修复            发现新 Bug
```

- **INIT**：初始化产物文件与迭代计数
- **SCAN**：review 代码 + 隔离环境运行测试，登记全部 Bug
- **PATCH**：按 P0 → P1 → P2 顺序修复所有条目
- **VERIFY**：网关 A，逐一验证旧 Bug 是否被测试证明修复
- **REGRESS**：网关 B，检查是否引入新 Bug
- **DONE**：终止循环，写总结报告

## 硬性约束（任何时候不得违反）

1. **迭代上限 = 3 次。** 每进入一次 PATCH 状态，迭代计数 +1（iteration = 1, 2, 3）。出现以下任一情况，必须**强制进入 DONE**，在 SUMMARY_REPORT.md 注明"自动化修复已达上限，请人工介入"，禁止继续修复：
   - 需要进入第 4 次 PATCH 的时刻（第 3 轮 VERIFY 后仍有未关闭条目，或第 3 轮 REGRESS 发现新 Bug）；
   - 第 3 轮循环结束后仍有未修复 Bug 或仍有新 Bug 产生。
   禁止以任何形式绕过计数（如"再试一次不算迭代""换个说法重跑"）。
2. **环境隔离。** 所有"运行项目"与"执行测试"的操作必须在临时 Docker 容器或虚拟环境中进行，严禁在宿主机直接运行生产级测试，严禁安装或修改宿主机全局依赖/环境。执行细则见"环境隔离"节。
3. **判定依据 = 测试用例 Pass/Fail。** 判定 Bug 是否修复只依据对应测试用例的通过/失败状态，禁止仅凭"看代码觉得修好了"下结论。若某 Bug 没有现成测试，先编写能复现它的测试用例，再判定。**修复必须通过修改生产代码实现，禁止通过修改/删除测试用例或断言来制造通过**；若确需修正测试本身（如期望值写错），须在 iteration_log.md 记录理由。绝不编造测试输出。

## 状态 0：INIT

1. 确定仓库根目录（产物文件写入此处）。
2. 检查产物：若 `bug_report.md` / `iteration_log.md` 已存在，说明是续跑，读取并沿用其状态与迭代计数；否则从零开始（iteration = 0）。
3. 检查隔离环境可用性：`docker --version`；无 Docker 时确认项目的虚拟环境方案（venv / uv / bun 等）。
4. 阅读项目配置（package.json / pyproject.toml / Makefile / Cargo.toml 等），确定依赖安装命令、测试命令、测试目录。

## 状态 1：SCAN（侦查基线）

1. **代码 Review**：通读项目结构与关键模块，形成基线认知。
2. **隔离环境运行生产级测试**（见"环境隔离"节）：
   - 先运行项目现有测试套件，收集全部失败；
   - 对测试未覆盖但 review 中发现的可疑点，编写复现测试并运行。
3. 将发现的每个 Bug 登记到 `bug_report.md`（全量清单，追加）：
   - 优先级定义：
     - **P0**：崩溃、数据丢失、主流程不可用、安全问题；
     - **P1**：主要功能异常、常见路径失败；
     - **P2**：轻微缺陷、边缘情况、体验问题。
   - 每条必须包含：ID（BUG-001 起）、优先级、复现步骤、预期行为、实际行为、报错日志。
4. 若测试全部通过且 review 未发现问题：如实报告"未发现 Bug"，生成 SUMMARY_REPORT.md 后直接进入 **DONE**，不伪造问题凑数。

SCAN 结束 → 进入 PATCH。

## 状态 2：PATCH（按序修复）

1. 读取 `bug_report.md` 中所有状态非 `[CLOSED]` 的条目。
2. **严格按 P0 → P1 → P2 顺序**修复（同优先级按 ID 升序）。
3. 修复一个优先级内的 Bug 时**不立即测试**，继续修复下一个，直到所有记录的 Bug 都完成"尝试修复"。期间对每个 Bug：
   - 修改代码；
   - 在 `iteration_log.md` 记录：iteration、Bug ID、修改的文件；
   - 在 `bug_report.md` 该条目追加一条"修复尝试"记录。
4. 全部尝试完毕后 → 进入 VERIFY。

## 状态 3：VERIFY（修复验证 · 网关 A）

1. 重新 review 修改后的代码，并在隔离环境重跑测试（先跑与修复相关的测试，再跑全量）。
2. 对 `bug_report.md` 中每个未关闭条目逐一判定（**只认测试结果**）：
   - 对应复现测试**通过** → 该条目标记为 `[CLOSED]`；
   - 对应复现测试**仍失败** → 该条目**保持未关闭**，更新记录：追加最新报错日志（保留全部历史日志，**不删除条目**）。
3. 决策：
   - 存在未关闭条目 → 返回 **PATCH**（进入下一轮，iteration +1）；
   - 全部关闭 → 进入 **REGRESS**。
   - 若 iteration 已达 3 仍需返回 PATCH → 强制进入 **DONE**（见硬性约束 1）。

## 状态 4：REGRESS（回归测试 · 网关 B）

1. 在隔离环境运行全量测试套件，与 SCAN 基线对比，找出修复引入的**新失败 / 新异常**（基线中不存在、修复后出现）。
2. 发现新 Bug：
   - 追加到 `bug_report.md`（新 ID，含优先级与复现步骤）；
   - 若 iteration < 3 → 返回 **PATCH**；
   - 若 iteration 已达 3 → 强制进入 **DONE**。
3. 未发现新 Bug → 进入 **DONE**。

## 状态 5：DONE（终止与归档）

1. 终止循环，停止一切修复动作。
2. 编写 `SUMMARY_REPORT.md`（模板见下），必须包含：迭代轮次、修复统计（发现/已关闭/未关闭，按优先级拆分）、测试覆盖率（执行了哪些测试、通过/失败数量）、是否全部解决、是否超出迭代上限。若超限，注明**"自动化修复已达上限，请人工介入"**；剩余未关闭 Bug 逐一列出并附失败证据。
3. 向用户汇报：结果摘要 + 三个产物文件的路径。

## 环境隔离（执行细则）

- **优先 Docker**（在仓库根目录执行）：

  ```bash
  docker run --rm -v "$PWD":/workspace:ro -w /workspace <镜像> \
    bash -lc "cp -r /workspace /work && cd /work && <安装依赖> && <测试命令>"
  ```

  - 宿主机挂载**只读**（`:ro`），容器内复制到 `/work` 再执行，宿主机工作区零污染；
  - 镜像优先选择项目自带 Dockerfile / devcontainer 镜像；否则用语言官方镜像（node:lts、python:3.x 等）；
  - 依赖安装与测试产物（缓存、临时文件）全部留在容器内，随 `--rm` 销毁；
  - 测试输出（报错日志）经标准输出取回，由宿主机侧的编辑工具写入产物文件。
- **无 Docker 时**：使用项目已有的虚拟环境机制（python -m venv、uv venv、bun/npm 本地依赖等），依赖安装与测试执行全部在该环境内；严禁安装/修改宿主机全局工具、全局依赖，或项目目录之外的任何文件。
- 代码修改与产物文件写入在宿主机完成，仅"运行"在隔离环境完成。

## 产物文件（仓库根目录）

### bug_report.md（动态更新的全量 Bug 清单）

```markdown
# Bug Report

| ID | 优先级 | 状态 | 标题 | 模块 | 首次发现 | 最后更新 |
|----|--------|------|------|------|----------|----------|
| BUG-001 | P0 | OPEN | 登录崩溃 | src/auth.ts | iteration 1 | iteration 2 |
| BUG-002 | P1 | [CLOSED] | 导出乱码 | src/export.ts | iteration 1 | iteration 1 |

## BUG-001 — 登录崩溃
- 优先级：P0
- 状态：OPEN（未修复）
- 复现步骤：
  1. ...
- 预期行为：...
- 实际行为：...
- 报错日志：（每次 VERIFY 追加，不删除历史）
  - [iteration 1] ...
  - [iteration 2] ...
- 修复尝试：
  - [iteration 1] 修改 src/auth.ts → 测试仍失败
```

状态字段只有两种：`OPEN`（未修复）/ `[CLOSED]`（已修复）。未修复条目只追加、不删除。

### iteration_log.md（每轮循环追加一节）

```markdown
# Iteration Log

## Iteration 1（PATCH → VERIFY → REGRESS）
- 修复目标：BUG-001 (P0)、BUG-002 (P1)
- 修改文件：
  - src/auth.ts — 修复 BUG-001
  - src/export.ts — 修复 BUG-002
- VERIFY：BUG-001 [CLOSED]；BUG-002 未修复（日志见 bug_report.md）
- REGRESS：发现新 BUG-003 (P2)
- 结论：进入第 2 轮
```

### SUMMARY_REPORT.md（DONE 时生成）

```markdown
# 修复总结报告
- 执行时间：
- 迭代轮次：3（上限 3）
- 发现的 Bug：5（P0×1、P1×2、P2×2）
- 已修复 [CLOSED]：3（P0×1、P1×1、P2×1）
- 未修复：2（P1×1、P2×1）
- 测试执行：单元测试 42/45 通过；集成测试 8/10 通过
- 是否全部解决：否
- 是否超出迭代上限：是
- 结论：自动化修复已达上限，请人工介入
- 剩余 Bug：
  - BUG-002 (P1)：...（失败证据摘要，详见 bug_report.md）
```

## 纪律

- 每个状态切换都基于实际观察到的测试输出，绝不编造或美化结果。
- 达到迭代上限后不得"再修最后一个"，直接 DONE 并如实报告。
- 产物文件只写事实：日志来自真实命令输出，状态来自真实测试结果。
