# 多 Agent 工作流原则

> 以下指南适用于编排子 agent 进行复杂、多阶段工作的场景。

## 核心原则

1. **先计划，后编码。** 对于非平凡任务，先计划，再执行，最后验证。每个阶段都要明确且可验证。

2. **按角色委派。** 使用专门的 agent 发挥其优势：
   - `architect` — 架构决策与权衡
   - `planner` — 任务分解与依赖映射
   - `product` — PRD 级范围界定与验收标准
   - `consultant` — 战略分析与决策框架
   - `consensus` — 从多个选项中收敛到唯一方案
   - `executor` — 实现与重构
   - `reviewer` — 代码审查与质量检查
   - `verifier` — 验收测试与回归检查
   - `debugger` — 问题诊断与根因分析
   - `researcher` — 文档查找与技术调研
   - `director` — 多角色团队编排
   - `editor` — 最终输出组装与润色
   - `quick` — 微小、低风险的修复

3. **最小化上下文负载。** 只读取当前步骤需要的内容。在移交给另一个 agent 之前做好总结。

4. **始终在最后进行验证。** 运行相关的测试和检查。报告变更的文件、已知风险以及后续操作。

5. **范围不明确时先判断意图。** 在行动之前，将任务分类为计划、执行、验证或研究。如果缺少验收标准，不要直接跳到实现。

## 团队流水线（适用于复杂工作）

当任务跨越架构、实现和验证时：

1. **计划** — `architect` + `planner` 分解任务并映射依赖。
2. **范围界定** — `product` 锁定范围、约束和验收标准。
3. **执行** — `executor` 逐个实现经过验证的切片。
4. **验证** — `reviewer` + `verifier` 检查正确性、回归问题和验收标准。
5. **修复** — 如果验证失败，`debugger` + `executor` 修复问题，然后重新验证。

重复执行 → 验证 → 修复，直到验收标准通过或阻塞问题被上报。

## 安全护栏

- 没有经过验证的证据，绝不宣称完成。
- 存在未解决的阻塞问题或未通过的验证关卡时，绝不宣布"完成"。
- 当被缺失的需求、缺失的权限或重复失败阻塞时，停止自主循环。
- 明确暴露阻塞问题——不要隐藏或压制它们。
