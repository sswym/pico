# pico 全流程用户体验复盘与优化分析

> 审查方式：以真实产品终端用户视角，完整走查 pico 的首次安装、初始化配置、日常会话、记忆使用、子代理委派、高级工具（网页/LSP/MCP/钩子/规划模式）等全部使用链路；结合源码级代码走读（`src/extensions/` 全部 20 个扩展 + `src/runtime/` + `src/setup/`）、上游 `@earendil-works/pi-*` 行为核验、实际命令行体验（`--help` / `setup --help`）交叉验证。
>
> 覆盖维度：功能体验、操作逻辑、界面交互、性能流畅度、细节适配、使用痛点、潜在 Bug、体验瑕疵。
>
> 每条问题标注严重程度：🔴 高（直接损害核心体验/数据安全）｜🟠 中（明显影响体验或功能可用性）｜🟡 低（细节瑕疵）。

## 一、用户全流程体验地图

| 阶段 | 用户动作 | 现状体验 | 核心问题 |
| --- | --- | --- | --- |
| 1. 安装 | `bun install` + 启动 | 启动有 ASCII logo，观感良好 | 无模型时仅有引导文案，需跳转 setup；帮助文本品牌混杂 |
| 2. 初始化 | `pico setup` | 向导分 section 较清晰 | `--non-interactive` 模式存在配置静默覆盖风险；`setup --help` 信息重复 |
| 3. 首次会话 | 提问 → agent 干活 | 流式输出 + 状态栏反馈较好 | 每轮对话前记忆预取恒未命中，启动延迟累加；LSP 冷启动易失败 |
| 4. 记忆使用 | 日常对话自动沉淀 | 自动提取 + 检索 + 命令面齐全 | **读写 scope 不对称导致记忆"隐形"**；中文检索质量差；误提取污染库 |
| 5. 任务管理 | todoWrite / F7 | 面板可视化好 | 模型微调措辞即强制展开面板；F7 无反馈；切换会话静默清空 |
| 6. 子代理 | subagent / `/implement` | 模式丰富、渲染较完整 | 中断丢失部分结果；孤儿进程；默认无超时；输出无上限灌回主会话 |
| 7. 高级工具 | web/LSP/MCP/hooks | 功能面完整 | 配置错误普遍静默；LSP 崩溃静默；plan 非交互死锁 |
| 8. 会话管理 | `/new`、resume、quit | 崩溃恢复提示是亮点 | logo 每次会话重现；todo 状态跨会话丢失无提示 |

## 二、问题清单（按主题分类）

### 2.1 启动、界面与主题体验

#### 🔴 2.1.1 每次启动无条件删除用户主题文件并强制覆盖主题选择
- **现象**：用户如果手工复制/编写过名为 `carbon.json`、`titanium.json`、`retro-terminal.json`、`quiet-slate.json` 的主题文件放到 `~/.pico/agent/themes/`，每次启动 pico 都会被静默删除（`rmSync(force: true)`）；随后 pico 强制 `setTheme("claude-code-dark")`，而上游的 `setTheme` 成功后会**持久化写入 settings.json**——用户用 `/theme` 或设置项选中的主题，重启后被强改回深色主题，且无任何提示。
- **根因**：`src/extensions/retro-theme/index.ts:51-67`。清理旧残留的意图正确，但按文件名无差别删除用户文件；且品牌主题被当作"唯一正确主题"无条件应用。
- **建议**：只清理带内部标记的文件（如文件头注释 `generated by pico`）；品牌主题改为**首次写入**而非每次覆盖；不主动调用 `setTheme` 持久化，仅当用户未显式配置过主题时才应用默认；主题应用失败时给出可见提示。

#### 🟠 2.1.2 自定义 logo 头不支持折叠，Ctrl+O 交互不一致
- **现象**：完整 logo 高 10-11 行且常驻屏幕顶部，小终端下占据近半屏；内置 header 支持折叠（Ctrl+O），而 pico 自定义 logo 组件未实现 `setExpanded` 折叠协议，Ctrl+O 对它静默失效——工具输出可折叠、logo 不可折叠，交互不一致。且每次 `/new`、resume 新会话都会重新展示完整 logo。
- **根因**：`src/extensions/logo/index.ts:160-177` 返回的容器组件缺少折叠能力；`session_start` 每次都渲染完整 logo。
- **建议**：为 logo 组件实现 `setExpanded`（折叠为单行 "pico"）；仅首次启动显示完整 logo，后续会话显示精简版；小终端（<60 行）自动降级。

#### 🟠 2.1.3 折叠预览按字符数截断，中文内容形同虚设
- **现象**：工具输出折叠预览按"180 字符 / 8 行"截断，但渲染时按**列宽**换行——180 个中文字符在 120 列终端实际占 12-16 行，"折叠 8 行"的承诺失效；"N more lines"提示与实际不符。窄终端（<100 列）下折叠与展开的视觉差异更小。
- **根因**：`src/extensions/ui/rendering.ts:14-21` 与 `src/extensions/tool-render.ts:95-112` 按字符数而非 `get-east-asian-width` 列宽计算。
- **建议**：截断逻辑统一改为列宽计算（项目中已有 `visibleWidth`/`truncateToWidth` 工具可直接复用）。

#### 🟠 2.1.4 展开大输出无防护，首帧渲染卡顿
- **现象**：展开工具输出时把完整内容（可达 MB 级，如大文件读取、base64 图像）一次性塞进 Text 组件，首次渲染 + TUI 差分比较 MB 级行会明显卡顿；超长单行的 wrap 成本更高。
- **根因**：`src/extensions/tool-render.ts:120-121` 展开模式无行数/宽度上限。
- **建议**：展开模式仍设硬上限（如 2MB 或 5000 行），超出部分提示"已截断，完整输出见 details"。

#### 🟡 2.1.5 页脚 git 状态在慢仓库下反复 spawn 进程
- **现象**：git status 500ms 超时即 kill 且不写缓存，下一帧又重试——在 NFS、超大仓库、`index.lock` 卡死场景下，流式输出期间每 1.2s spawn 一个新 git 进程，与上游自身的 git watcher 形成双重开销。
- **根因**：`src/extensions/retro-theme/footer.ts:118-133` 超时不缓存、`202-213` 立即重试。
- **建议**：超时结果写入短暂缓存（如 30s），并记录连续失败次数做指数退避。

#### 🟡 2.1.6 输入框装饰与编辑器内部布局宽度不一致
- **现象**：多行输入时光标换行位置与视觉换行点差 1 列；autocomplete 下拉行也被加 "❯ " 前缀整体右缩，且空输入特判路径与正常路径前缀处理不一致。
- **根因**：`src/extensions/input-history/index.ts:110-126` 以 `width-2` 渲染、按 `width-3` 装饰。
- **建议**：装饰逻辑改为在渲染结果之外拼接前缀，或统一按装饰后宽度计算 wrap。

#### 🟡 2.1.7 工作指示行的工具名未截断
- **现象**：`tool <name> Ns` 中工具名（如 `typescript-language-server`）超长时撑满并错位换行。
- **根因**：`src/extensions/retro-theme/activity.ts:94-102` 直接拼接。
- **建议**：按剩余宽度截断工具名。

#### 🟡 2.1.8 终端控制序列清洗遗漏 DCS/APC
- **现象**：工具输出中的 DCS 序列（kitty 图像协议、Sixel 探测输出）会原样透传终端，可能触发图像渲染或垃圾字符。
- **根因**：`src/extensions/ui/rendering.ts:23-32` 只覆盖 OSC/CSI。
- **建议**：补充 DCS（`\x1bP...\x1b\`）与 APC 序列剥离。

#### 🟡 2.1.9 主题工具提示与快捷键硬编码
- **现象**：todo 面板折叠提示写死 "F7"，用户重绑快捷键后提示失真；折叠状态下按 F7 无任何视觉反馈（不提示"当前无任务"）。
- **根因**：`src/extensions/todo/widget.ts:93,138`。
- **建议**：从 keybindings 配置读取实际键位；无任务时按 F7 给出一次性提示。

### 2.2 首次使用与配置引导

#### 🔴 2.2.1 报错/引导文案指向不存在的配置文件（models.yml）—— ✅ 已修复
- **现象**：推理模型 400 引导与无模型引导均指示用户编辑 `~/.pico/agent/models.yml` 并在其中加 `compat` 字段，但**运行时只读取 `models.json`**（`pico setup` 自定义 provider 也写入 JSON）。用户照做后 400 依旧，误以为"修复无效/配置被忽略"；`/doctor` 的配置扫描与建议文案同样错位。另：`PICO_HOME` 重定位后硬编码的 `~/.pico/agent` 路径不存在。
- **根因**：`src/extensions/guidance/index.ts:63-79` 硬编码路径与文件名；`src/extensions/doctor/config-scan.ts:237,267` 扫描对象与实际读写文件不一致。
- **修复**（已完成）：引导文案改为动态路径并指向 `models.json`；`/doctor` 推理 compat 扫描改为 JSON 解析（provider 级/模型级 compat 均可识别）。
- **建议**：统一改用 `paths.ts` 导出的 `picoModelsPath()` / `picoSettingsPath()` 动态路径，文案改为 `models.json`；`/doctor` 扫描逻辑与 setup 写入格式对齐。

#### 🟠 2.2.2 配置类错误普遍静默（console.warn 在 TUI 下不可见）
- **现象**：MCP 配置 JSON 损坏、hooks 配置非法、`subagent.json` 语法错误、agent frontmatter 缩进错误——这些全部只 `console.warn` 一次后静默降级。TUI 用户看不到 stderr，表现为：配置了 MCP 但状态栏 "0 connected"；安全钩子静默不执行（用户以为有保护）；子代理模型/超时覆盖不生效却无任何界面提示。
- **影响面**：`src/extensions/mcp/config.ts:33-41`、`src/extensions/hooks/config.ts:36-42`、`src/extensions/subagent/config.ts:28-32`、`src/extensions/subagent/agents.ts:214`。
- **建议**：建立统一的"配置告警"通道（如 session_start 时通过 `sendMessage` 一次性汇总展示，或 `/doctor` 集中列出）；对安全相关配置（hooks、MCP）失败必须可见。

#### 🟠 2.2.3 项目级功能默认关闭但无任何提示
- **现象**：项目里放了 `.pico/hooks.json`、`.pico/mcp-servers.json`、`.pico/lsp.json` 等配置，因安全开关未开被**静默忽略**，用户配置了却毫无反应，也不知道要去哪里开。
- **根因**：`src/extensions/mcp/config.ts:93-102` 等加载路径无提示。
- **建议**：检测到项目配置文件存在但被开关禁用时，在 session_start 提示一次（"检测到项目 MCP 配置，当前被安全策略禁用，运行 `/doctor` 查看如何开启"）。

#### 🟠 2.2.4 向导与帮助的品牌混杂
- **现象**：`pico --help` 打印完 pico 品牌头后，上游帮助段仍显示 "pi - AI coding assistant"、命令名 `pi install`/`pi config`——用户会疑惑自己用的到底是 pico 还是 pi；`pico setup --help` 与 `pico --help` 打印相同的 pico 特有命令头部，信息重复。
- **根因**：`bin/pico.ts` 的品牌层只加了前缀，未替换上游帮助正文。
- **建议**：拦截上游 help 文本，做 `pi → pico` 品牌替换（至少替换标题行与命令名前缀）；`setup --help` 跳过通用头部。

### 2.3 记忆系统（核心卖点，问题最集中）

#### 🔴 2.3.1 读写 scope 不对称——自动提取的记忆默认"隐形"
- **现象**：会话中自动提取的事实默认存为 `project:<cwd>`（只要 session 有 cwd），而 `memory(search/probe/list/related/reason)` 工具默认 `scope=global`。**绝大多数自动沉淀的记忆在默认检索下完全不可见**——模型按系统提示"先 search"却得到 0 条，误判"用户没有相关记忆"；用户也感知为"记忆系统像没在工作"。工具描述未说明默认不含项目事实。
- **根因**：`src/extensions/memory/extract.ts:146`（写入端默认 project）+ `src/extensions/memory/store.ts:395-409` / `tool.ts`（读取端默认 global）。
- **建议**：检索默认改为"当前项目 scope（含 global）"与写入端对齐；或自动提取改为 global（需评估隐私权衡）。同时更新工具描述与 `memory-tool.md` 提示词。

#### 🔴 2.3.2 中文检索基本失效，子串回退甚至"否定反转"
- **现象**：FTS5 默认 tokenizer 把连续汉字当一个 token（"我更喜欢"整体一个），查询侧同样按 run 切分——中文字段级匹配几乎全灭，每次中文查询都落入子串回退。子串匹配的后果：**"我不用 bun" 会命中查询 "bun"**（否定内容被当正相关返回）、"bun" 命中 "bundle"；排序 = 命中词数 × trust，短通用词霸榜。TF-IDF 向量对中文同样因 run 切分近乎无效，40 个硬编码 CJK 词只是补丁。
- **根因**：`src/extensions/memory/store.ts:340-353, 634-662`、`src/extensions/memory/tfidf.ts:36-50`。
- **建议**：短期——FTS 改 `tokenize='unicode61'` 加 trigram tokenizer（SQLite FTS5 trigram 支持中文子串索引），或查询侧按字符 bigram 切分后再 FTS；回退排序引入否定词过滤（"不/没/别"后 2 词内的词降权）与词性权重。中期——引入真实 embedding 检索（路线图已有 v2 记忆计划）。

#### 🔴 2.3.3 memory.db 损坏导致整个 pico 无法启动
- **现象**：一次异常断电/磁盘错误后 `memory.db` 损坏（SQLITE_CORRUPT），`new Database()` 抛错，`ProviderManager` 在扩展工厂顶层无 try/catch——**pico 直接启动失败**，用户只能手动删除 `~/.pico/memory.db`，全部记忆丢失。对比之下 demo 用的 holographic provider 反而有损坏备份恢复逻辑。
- **根因**：`src/extensions/memory/store.ts:104-120` + `src/extensions/memory/provider-manager.ts:72-79`。
- **建议**：构造失败时备份损坏文件（`memory.db.corrupt-<ts>`）重建空库，并在会话中提示用户；启动路径整体加保护，任何单扩展失败不应阻断整个产品。

#### 🔴 2.3.4 `/memory clear` 清空所有项目记忆，`remove` 可跨项目越权
- **现象**：`/memory clear` 执行 `DELETE FROM facts` **无 scope 过滤**——在项目 A 执行 clear，项目 B/C 的记忆与全局用户画像全部永久消失（确认弹窗只显示总数，用户无从得知包含其他项目）；`/memory remove <id>` 无确认、无 undo，任意会话可通过 ID 枚举删除其他项目的事实；`update`/`feedback` 同样无 scope 归属校验。
- **根因**：`src/extensions/memory/command.ts:241-253`、`src/extensions/memory/store.ts:322-327, 253-276`。
- **建议**：clear 增加 scope 参数与二次确认（列出各 scope 计数）；remove/update 校验 fact 归属；删除操作先写回收表或至少导出备份。

#### 🔴 2.3.5 纠正检测宽匹配误触发，反向破坏真实记忆
- **现象**："actually, I want…"、"I said…"、"don't do that" 等口语高频表达被识别为纠正，**整段消息**以 0.7 高信任入库并双写 curated MEMORY.md，同时把旧事实扣 0.3 信任；且该检测在 `turn_end` 每轮执行。日常对话中的"实际上我想要…"变成"纠错"，垃圾 correction 反排最前，真实记忆被系统性降权。
- **根因**：`src/extensions/memory/extract.ts:38-51`（正则过宽）+ `index.ts:250-256`（每轮执行）。
- **建议**：纠正检测要求上下文（如"上一条/你刚才说的 X 不对"式结构）而非单句匹配；降低整段入库长度（如 200 字符）；correction 触发扣信任前增加确认（交互模式可弹确认）。

#### 🟠 2.3.6 误提取：求助被当偏好、失败教训入库
- **现象**："I want to fix this bug"、"程序报错了帮我看看" 等**一次性求助**被存为 `user_pref`/`failure`；"I never said that"（纠正场景）因不匹配纠正模式被存成偏好，语义完全反转；`text.length < 10` 跳过又漏掉 "用 bun"、"别用 npm" 这类最精炼的偏好表达；匹配指令模式即跳过整条消息，混合内容漏存；所有提取失败被 `catch {}` 静默吞掉。
- **根因**：`src/extensions/memory/extract.ts:20-27, 64-72, 100-108, 146-151, 176-178`。
- **建议**：提取前做意图分类（疑问句/命令式/求助语气的消息跳过）；提取结果在工具返回中可见（"已记住：…"），失败可感知；引入置信度阈值，低置信事实以低 trust 入库。

#### 🟠 2.3.7 project scope key 未规范化，同一项目记忆分裂
- **现象**：scope key 直接拼接原始 cwd：`/home/u/proj` vs `/home/u/proj/`、符号链接路径、子目录会话（cwd 为项目子目录）、大小写差异——各自成为独立 scope，同一项目在不同目录形态下打开时记忆互相不可见，自动提取的事实碎片化分布。
- **根因**：`src/extensions/memory/query-scope.ts:6-8`。
- **建议**：规范化 cwd（`realpath` + 去尾斜杠）；子目录会话向上查找最近 `.git`/`package.json` 作为项目根。

#### 🟠 2.3.8 安全策略存在后门：PICO_MEMORY_DENY 与密钥扫描均可绕过
- **现象**：`PICO_MEMORY_DENY` 屏蔽词只在工具写入路径生效，`turn_end` 纠正与 `agent_end` 自动提取直接 `store.add` 绕过；密钥扫描只扫 content 不扫 tags（"把密钥放 tags 里"即绕过）；驼峰 key 名（`accessKey=`）、JWT（`eyJ...`）、base64/hex 编码密钥全部漏扫；holographic demo 后端 update 完全不扫描且明文落盘。
- **根因**：`src/extensions/memory/builtin-provider.ts:39-42`、`store.ts:149,156`、`secrets.ts:22-43`、`holographic-provider.ts:126-141`。
- **建议**：屏蔽词与密钥扫描下沉到 store 层统一执行；补 JWT 与驼峰模式；tags 纳入扫描。

#### 🟠 2.3.9 `/memory related/reason` 对项目事实永远失效
- **现象**：`/memory related bun`、`/memory reason A,B` 不解析 `--scope` 参数、不传 cwd，retriever 默认 scope=global——**项目事实永远搜不到**；且 retriever 在候选为空时直接返回空、不做子串回退（与 search 行为不一致），中文实体几乎必然空结果。此外 `related` 排序 = 共现×0.5 + trust×0.5，共享实体多的"热门"事实在所有查询里霸榜。
- **根因**：`src/extensions/memory/command.ts:192-211`、`src/extensions/memory/retrieval.ts:97-106, 249-339`。
- **建议**：related/reason 支持 `--scope` 并默认与 search 对齐；为空时回退子串；排序引入查询相关性权重。

#### 🟠 2.3.10 每轮对话记忆预取缓存恒未命中
- **现象**：预取缓存命中条件是"新查询以旧查询为前缀"，而缓存由上一轮整条用户消息入队——下一轮消息几乎不可能以它为前缀，导致**每轮 agent 启动前都同步执行一次全库检索 + `_bumpRetrieval` 写库**（读路径恒定写放大），大库时启动延迟累加，`retrieval_count` 统计被污染。
- **根因**：`src/extensions/memory/provider-manager.ts:356-369` + `store.ts:412-423`。
- **建议**：缓存命中改前缀/相似度匹配；`_bumpRetrieval` 节流（如同一 fact 5 分钟内只 bump 一次）。

#### 🟡 2.3.11 `/memory` 命令面的细节问题
- **现象**：`/memory` 无参直接刷 50 行 list（新手看不到用法）；`list` 无分页无 `--limit`，大库时低信任事实不可见；`add` 用正则猜前缀，内容以 category 词开头的正常文本被错分；`remove` 无确认；`count` 无 scope 分布；`status` 不显示 curated notes 用量（2200/1375 上限）——`note_add` 满额被拒时无预警；`notes add/replace` 成功后**当前会话快照不更新且无提示**，用户继续对话发现模型没按新 note 回答，以为写入失败。
- **根因**：`src/extensions/memory/command.ts` 各子命令 + `curated-store.ts:66-88` 快照冻结。
- **建议**：无参显示简短帮助；list 加分页；notes 写入后提示"将在下个会话生效"，或通过 `events.ts` 通知刷新快照。

#### 🟡 2.3.12 别名单向扩展，"TS"↔"typescript" 只通一半
- **现象**：查询侧会把 "TS" 扩展成 "typescript"，但存储侧不做别名归一——存的是 "TS" 时搜 "typescript" 落空。用户最典型的"我记得存过但搜不到"场景。
- **根因**：`src/extensions/memory/synonyms.ts:12-28`。
- **建议**：存储侧写入时做别名归一化（alias → canonical 后再计算向量）。

#### 🟡 2.3.13 curated notes 双写与跨项目泄漏
- **现象**：同一消息在 `agent_end` 同时进 fact 库和 curated notes（两套 pattern 独立演进）；curated 无 scope——项目 A 的约定写入**全局** MEMORY.md 注入所有项目，造成跨项目"幻觉性记忆"；精确去重导致标点微差即重复添加，字符上限快速耗尽；用户手改过 MEMORY.md 后所有后续写入被永久拒绝（drift 守卫），backup 文件散落无清理。
- **根因**：`src/extensions/memory/curated-store.ts:34-49, 172-179, 287-345` + `index.ts:273-277`。
- **建议**：curated 自动提取改为"先归一化再去重"；考虑 notes 也支持 scope；drift 守卫改为合并策略并提示用户。

### 2.4 子代理体验

#### 🔴 2.4.1 中止只杀直接子进程，孙进程成孤儿
- **现象**：Ctrl+C 或超时中止子代理时，`killProc` 只对直接 pico 子进程发 SIGTERM/SIGKILL，未建进程组——子代理正在跑的 `bun test`/`npm install` 等**孙进程不随中止终止**，后台残留孤儿进程继续跑测试/安装/写文件（可能正在写已被清理的 worktree），占用 CPU、持有文件锁、污染仓库。同一代码库内 gates.ts 的 evidence 命令却用了 detached+进程组击杀，做法不一致。
- **根因**：`src/extensions/subagent/process.ts:130-142`。
- **建议**：spawn 时 `detached: true` 建独立进程组，中止时 `process.kill(-pid)` 组杀（对齐 gates.ts 做法）。

#### 🔴 2.4.2 内置 16 个 agent 全部无默认超时
- **现象**：`timeoutMs` 仅在 agent frontmatter 配置时生效，而 `src/prompts/agents/*.md` 里没有任何一个内置 agent 设置 `maxExecutionTimeMs`——子代理陷入模型挂起/工具死循环时无限运行，唯一出路是手动 Ctrl+C，与"慢首 token 无反馈"叠加后体验极差。
- **根因**：`src/extensions/subagent/process.ts:193` + 内置 agents 无配置。
- **建议**：代码层加默认超时（如 30 分钟），frontmatter 可覆盖；超时前给出可见警告。

#### 🔴 2.4.3 spawn 失败错误详情被丢弃
- **现象**：子进程 spawn 失败（命令不存在、权限不足、PATH 问题）时 `proc.on("error")` 直接 `resolve(1)`，Error 详情丢失——用户看到 "Agent failed: (no output)"，完全无法诊断。
- **根因**：`src/extensions/subagent/process.ts:182-184`。
- **建议**：把 error.code/message 并入失败结果（"Failed to spawn pico: ENOENT — 请检查 PATH"）。

#### 🟠 2.4.4 首条消息前无任何反馈
- **现象**：子代理结果面板在收到首个 json 事件前完全空白；慢模型首 token 等待 10-60s+，并行模式要等第一个任务产出才有 "Parallel: 0/4 done"。用户不知道代理是否在跑、是否卡死。
- **根因**：`src/extensions/subagent/orchestrator.ts:146-151,172` 无初始 "(running...)" 发射。
- **建议**：spawn 后立即发射 running 状态（含已耗时秒数）。

#### 🟠 2.4.5 Ctrl+C 中断后已完成结果全部丢失
- **现象**：并行跑 4 个任务、3 个已完成时按 Ctrl+C，`Promise.all` 整体拒绝，已完成任务的产出对主 agent 和用户完全不可见，只能重跑；链式模式同理。验收门阶段用户中止还被误报为 "Acceptance gate failed"（归因误导）。
- **根因**：`src/extensions/subagent/orchestrator.ts:176,394` + `gates.ts:83-94`。
- **建议**：中止时返回已完成的 partial results（标注 aborted）；gate 中止与失败分开报错。

#### 🟠 2.4.6 输出无上限灌回主会话，上下文被污染
- **现象**：并行模式每个任务输出截断到 50KB 后**全部内联**进工具结果（8 任务最坏 400KB）；单模式成功输出完全不截断（100KB+ 的 worker 最终输出全量吞入）；失败任务输出同样全量内联。一次委派即可烧掉主会话大半上下文窗口。
- **根因**：`src/extensions/subagent/orchestrator.ts:486-493, 521-527`。
- **建议**：主会话内联上限（如 8KB/任务），完整输出落临时文件并在结果中给路径（保留至会话结束）。

#### 🟠 2.4.7 链式 `{previous}` 无上限注入、占位符静默降级
- **现象**：`{previous}` 直接内嵌上一步完整输出（可达 MB 级），第 2 步上下文爆炸；`{outputs.xxx}` 拼错 key 时替换为字面文本 `(output "x" not found)` 而非报错，agent 可能顺着幻觉继续干；第一步里的 `{previous}` 被替换为空串。file-only 模式下 spill 文件在 finally 中被删除，但消息保留 "Output written to file (N bytes): /tmp/..." 路径——链式下游拿到的是**已删除文件的路径**，主 agent 尝试 read 也失败，完整输出实际丢失。
- **根因**：`src/extensions/subagent/orchestrator.ts:396`、`chain.ts:14,17`、`output.ts:36-42`。
- **建议**：`{previous}` 截断到上限（如 32KB）并注明截断；占位符未找到直接报错；spill 文件延迟到会话结束再清理。

#### 🟠 2.4.8 验收门（gate）体验问题
- **现象**：evidence 命令串行执行、最长各 60s，期间**零 UI 反馈**（多个命令时工具像死了一样挂几分钟）；selfRepair 每次返工都是完整 agent 调用，无超时无进度——gate 反复失败 + repair 反复跑 = 用户视角的"伪死循环"，且都是真金白银的 token 消耗；evidence 失败输出截 500 字符/前 5 行，`bunx tsc` 这类错误详情常被截掉关键诊断部分；criteria 与 evidence 按下标隐式配对，顺序错位即误报失败。
- **根因**：`src/extensions/subagent/gates.ts:146-147, 169-177, 213-221`。
- **建议**：gate 执行期间输出逐条进度；repair 前先问用户或显示预估成本；失败详情保留完整输出（落盘）；配对规则显式化（命名键或校验长度一致）。

#### 🟡 2.4.9 配置错误界面不可见（与 2.2.2 同类）
- **现象**：`subagent.json` JSON 损坏、agent frontmatter 缩进错误均只 console.warn——模型/超时覆盖静默不生效、自定义 agent 从列表消失，用户无感知。
- **根因**：`src/extensions/subagent/config.ts:28-32`、`agents.ts:214`。
- **建议**：同 2.2.2，统一配置告警通道。

#### 🟡 2.4.10 worktree 模式边界情况
- **现象**：非 git 仓库用 `isolation: worktree` 整批失败且不降级（不提示改用 none）；merge 冲突时工作树目录被删只剩分支（手动解决冲突只能纯命令行）；`pico-subagent` 固定身份提交且 `--no-verify` 跳过 hooks（用户 git log 出现陌生人提交、CI 钩子被绕过但不知情）；fork 的 session 文件无清理，频繁 fork 积累垃圾分支。
- **根因**：`src/extensions/subagent/worktree.ts:62, 74-82, 170-186`、`session.ts:12-29`。
- **建议**：非 git 仓库自动降级并提示；冲突保留工作树目录；提交身份/`--no-verify` 行为在工具描述中明示或加配置开关。

### 2.5 工具链（web / LSP / MCP / hooks / plan / ask / todo / vision / rtk / cache-optimizer）

#### 🔴 2.5.1 LSP 冷启动失败后被锁 3 分钟
- **现象**：初始化走 30s 超时——rust-analyzer 等冷启动（首次索引大项目）超过 30s 即判失败并进入 3 分钟 backoff，期间**所有 lsp 调用**都报 "Server failed to start recently… Retry in Ns"。新项目首次使用 LSP 大概率失败，然后被锁 3 分钟。
- **根因**：`src/extensions/lsp/client.ts:50-53` + `manager.ts:152-163`。
- **建议**：初始化超时放宽（如 90s）或改为后台重试不阻塞；backoff 期间允许手动重试。

#### 🔴 2.5.2 LSP 服务器崩溃后写操作完全静默
- **现象**：write/edit 后的诊断同步处理器整体包在 `catch {}` 里（注释明说 "Silently ignore writethrough failures"）——服务器崩溃时挂起请求全部被拒，但用户写完文件**得不到任何诊断、任何错误提示**，模型误以为代码没问题。崩溃重启后旧文档状态丢失，workspace diagnostics 变空（只重开第一个文件）。
- **根因**：`src/extensions/lsp/index.ts:377-389`、`client.ts:131-145`。
- **建议**：崩溃时至少在工具结果中追加一条可见提示（"LSP 已断开，诊断不可用，已跳过"）；重启后重开已打开文档。

#### 🟠 2.5.3 webFetch 内网无逃生口 + 缓存无法刷新 + 1MB 截断无提示
- **现象**：内网用户（公司 wiki、本地文档站）永远无法 fetch，`allowPrivateNetwork` 存在于内部选项却没有任何工具参数或配置暴露它；15 分钟缓存无法强制刷新，动态页面（CI 状态页）持续读到过期内容；响应体 1MB 截断时若转 Markdown 后 <8KB，用户拿到不完整页面**却没有任何提示**；`http://` 被静默升级 https 后失败不解释原因。
- **根因**：`src/extensions/web/fetch.ts:120-124, 213-219, 331-352, 426-438`。
- **建议**：工具参数增加 `allow_private_network`（或 settings 白名单）；增加 `bypass_cache` 参数；截断时在结果中明示 "响应已截断（原始 1.4MB）"。

#### 🟠 2.5.4 webSearch 输出无截断
- **现象**：25 条结果 × 长 snippet（Tavily content 可达数百字/条）轻松超过 10KB 进入模型上下文——webFetch 有 8KB 上限，webSearch 没有。hybrid 模式单 provider 降级仅 console.warn，用户拿到半覆盖结果而不知情。
- **根因**：`src/extensions/web/search.ts:425-439, 352-366`。
- **建议**：总量截断（如 12KB）按 URL 去重后保留最相关；降级时结果中注明 "Exa 不可用，仅返回 Tavily 结果"。

#### 🟠 2.5.5 cache-optimizer 对第三方 OpenAI 兼容网关注入 prompt_cache_key 导致 400
- **现象**：只要 api 名含 "openai-completions" 就注入 `prompt_cache_key` 请求字段——vLLM、Ollama 兼容层、自建代理等第三方网关同样匹配，若网关不支持该字段则**所有请求 400**；key 用截断的 session id，长 id 截断后可能碰撞、跨会话共享缓存键。系统提示重排（stable 前置 + `---` 分隔）不保证指令顺序语义，模型对顺序敏感时行为漂移且无日志可查。
- **根因**：`src/extensions/cache-optimizer/index.ts:262-274, 221-228, 283-290, 318-332`。
- **建议**：仅对白名单官方端点（api.openai.com 等）注入；失败 400 时自动重试去掉该字段并降级；重排前记录原始顺序（debug 日志），仅在有明显收益（官方端点）时启用。

#### 🟠 2.5.6 规划模式在非交互模式下死锁
- **现象**：`-p`/CI 模式未设 `PICO_ALLOW_UNATTENDED_PLAN_APPROVAL` 时，ExitPlanMode 永远返回"需交互审批"，模型被困在计划模式，批处理任务死锁只能杀进程；且 `/plan` **只能进不能出**（没有 `/plan off`），交互模式下用户也无法主动解除只读锁定（只能 /reload）。计划模式还把 `webSearch`/`askUserQuestion`/`todoWrite` 一并封禁，调研能力受限。
- **根因**：`src/extensions/plan/index.ts:228-249, 34, 199-201`。
- **建议**：非交互模式下超时（如 3 分钟）自动返回"计划未批准"并退出计划模式；增加 `/plan off`；允许列表加入 webSearch/askUserQuestion。

#### 🟠 2.5.7 MCP 服务器崩溃不重连、超时后副作用重复
- **现象**：MCP 服务器进程中途退出后所有 `mcp__*` 工具报 "not active (server disconnected or reconnecting)"，`connect()` 只在 session_start 执行——用户只能 /reload 恢复；工具调用 30s 超时后**服务器侧继续执行**，模型重试可能重复副作用（如重复写库、重复发请求）；服务器 id 含 `__`/空格时工具名歧义；home 与 project 同名 server 覆盖时旧工具注册残留。
- **根因**：`src/extensions/mcp/index.ts:282-289, 128-133, 190-206` + `client.ts:38-40, 152-166`。
- **建议**：检测到断开自动重连（指数退避）；超时后尝试通知服务器取消（如 `notifications/cancelled`）；工具描述中明示"超时不代表取消"；覆盖时注销旧工具。

#### 🟠 2.5.8 hooks 安全钩子静默失效 + 无递归防护
- **现象**：hooks 配置错误只 console.warn（安全钩子 PreToolUse 校验静默失效，用户以为有保护）；`turn_end` 的 PostUserMessage 钩子同步 await，慢钩子每次用户发消息后都卡 UI；PreToolUse 阻塞钩子默认 30s 无响应窗口（工具调用看似卡死）；钩子命令里调用 `pico` CLI 无递归防护（无限嵌套）；项目层无法覆盖 home 层同名钩子（去重保留先出现者）。
- **根因**：`src/extensions/hooks/config.ts:36-42, 120-123` + `runner.ts:60-66` + `index.ts:26-31, 88-92, 133-156`。
- **建议**：安全类钩子加载失败必须可见（同 2.2.2）；PostUserMessage 异步化；阻塞钩子加进度提示（"等待钩子执行…N s"）；检测钩子命令自身调用 pico 时跳过（环境变量标记）。

#### 🟠 2.5.9 ask 与 vision 的交互细节
- **现象**：用户 Esc 取消提问后模型常会重试调用 → 同一问题反复弹窗打扰；preview 无长度限制，多行 preview 直接拼接进选项 label，TUI 渲染可能错乱；多选每次选择都重新弹 select、无法撤销。vision 侧：主模型不支持视觉时，单图分析失败该图被直接丢弃（内容永远丢失）；未配置辅助模型时贴图无任何提示（图片原样传给不支持图片的模型）；vision 模型调用无独立超时，provider 挂起时无限等待。
- **根因**：`src/extensions/ask/index.ts:54-66, 110-132, 157-162`、`src/extensions/vision/index.ts:56-59, 69-76`、`analyze.ts:196-216`。
- **建议**：取消后给模型返回明确"用户已拒绝，不要重试"语义（或结果里带 cancelled 标记让模型不再重试）；preview 限长；多选支持一次多选确认；vision 失败保留原图并注明分析失败；补 wall-clock 超时。

#### 🟠 2.5.10 rtk 包装破坏管道/重定向/命令链语义
- **现象**：`git log | head -20` → 只给整条命令加 rtk 前缀，rtk 已压缩输出又被 head 截断；`git diff > /tmp/x` → 压缩文本写入文件，重定向语义破坏；`git add . && git commit` → 只有第一个命令被包裹（与 AGENTS.md 声称的"链中每个命令都用 rtk"不符）；`cargo run`（长驻 dev server）被误判为可压缩命令，输出被过滤（LONG_RUNNING_FLAGS 只覆盖 watch/follow 类 flag）。
- **根因**：`src/extensions/rtk/index.ts:31-46, 106-124, 168-178`。
- **建议**：检测管道/重定向/`&&`/`||` 时跳过 rtk（或按段分别包裹）；`cargo run`/`go run`/`bun run` 等长驻命令列入排除名单。

#### 🟡 2.5.11 LSP 诊断等待窗口的体验问题
- **现象**：`diagnostics` 文件模式固定 sleep 500ms 后读缓存——慢服务器 500ms 内没 publish 就返回空/旧诊断，模型误判"无诊断=无错误"；每次写文件后最多白等 5.5s（inline 500ms + 后台 5s），不支持 save 后诊断的服务器让每次干净写入都卡 5 秒以上；用户首次 decline LSP 安装后，后续所有 lsp 调用静默返回 "No language server available"，不再解释原因；启动失败原因只进 stderr（TUI 不可见）；`spawnSync tsc --help` 与 `prewarmProject` 同步扫目录在 session_start 路径上，大仓库启动 UI 冻结数秒。
- **根因**：`src/extensions/lsp/index.ts:160-203, 270-290, 341-351`、`manager.ts:56-81, 297-329, 331-344`。
- **建议**：诊断改为事件驱动（路线图已列）；写后等待改为"收到 publish 即返回，超时 2s"；拒绝安装后每次调用附带原因提示；同步探测改异步；workspace diagnostics 对未打开文件明确标注"仅覆盖已打开文件"。

#### 🟡 2.5.12 todo 列表的交互细节
- **现象**：模型微调任务措辞（很常见）即触发"新任务"判定，面板从折叠态强制展开打断用户；最后一个任务完成后面板自动清空，"已完成"展示消失；切换会话静默清空 todo 列表无提示；writtenTodos 重复 id 重分配后模型用旧 id 提交会再次重分配，警告文案只说 "Use the returned ids" 未必理解。
- **根因**：`src/extensions/todo/widget.ts:116-126`、`store.ts:46-70, 51-56`、`index.ts:150-160`。
- **建议**：折叠判定改为"任务数增加"而非内容变化；完成态保留一行汇总；切换会话时提示"该会话的任务列表为空"。

### 2.6 稳定性、数据安全与资源

#### 🔴 2.6.1 记忆误存导致隐私/泄露面
- **现象**：密钥扫描存在多个绕过面（见 2.3.8），含真实密钥的记忆可能被持久化明文到 `~/.pico/memory.db`；curated 快照中 blocked 条目仅从提示中隐藏，磁盘原文保留——安全上只是防注入，非防泄漏。系统提示还鼓励"add 用户分享的内容"，密钥出现在聊天里时会被 LLM 顺手存下。
- **建议**：扫描下沉 store 层 + 补模式（见 2.3.8）；对敏感类别（credential）事实默认不入库，只提示不存储。

#### 🟠 2.6.2 长会话内存与扫描开销线性增长
- **现象**：`agent_end` 对累积的所有历史消息重跑 ~30 个提取正则（幂等靠 UNIQUE 去重，但开销每轮累加），`sessionMessages` 无限累积（builtin provider 无 onSessionEnd 消费者）；检索侧 `_bumpRetrieval` 每次命中都写库。长会话后期每轮结束有秒级 GC/扫描开销。
- **根因**：`src/extensions/memory/index.ts:271-282` + `store.ts:412-423`。
- **建议**：只扫描"本轮新增消息"；设置消息缓冲上限（如最近 200 条）；bump 节流。

#### 🟠 2.6.3 stderr 无上限累积
- **现象**：子代理 stderr 无截断地累积进内存；失败时 `getResultOutput` 可能把海量 stderr 灌进错误消息；成功路径永远不展示 stderr（调试日志刷屏时用户无从查看）。
- **根因**：`src/extensions/subagent/process.ts:146-151`。
- **建议**：stderr 截断（如 256KB）并保留尾部；失败时展示尾部 + 落盘路径。

### 2.7 品牌、文案与一致性

#### 🟡 2.7.1 文档/文案不一致
- **现象**：`subagent` 工具描述写 "Built-in agents: scout, planner, worker, reviewer, oracle, researcher"（6 个），实际内置 16 个（verifier、debugger、architect、consensus 等已存在但用户不知道）；README 声称的测试数与实际文件数不符（小版本迭代后未同步）；`docs/internal-tech-review.md` 的"已知局限"未随修复更新。
- **建议**：工具描述改为"16 个内置角色，`/help` 查看全部"；发布前核对 README 数字。

#### 🟡 2.7.2 上游透传信息的品牌泄漏
- **现象**：除 2.2.4 的 help 外，无模型引导、崩溃提示等文案中仍可能出现上游 "pi" 字样；`--version` 显示 "pico 0.1.0 (upstream pi 0.83.0)" 对普通用户是噪音。
- **建议**：版本输出可加 `--verbose` 才显示上游版本。

## 四、优化落地建议（按主题打包）

### 4.1 记忆系统（优先修复，投入产出比最高）
1. **检索默认 scope 与写入对齐**：无显式 scope 时按当前 cwd 检索（project + global 混合），同时更新工具 schema 描述与 `memory-tool.md`。
2. **中文检索升级**：FTS5 trigram tokenizer（零依赖，SQLite 内置）或查询侧 bigram 切分；子串回退加否定词过滤。
3. **启动自愈**：数据库损坏时自动备份 + 重建 + 提示，绝不让记忆问题阻断产品启动。
4. **clear/remove 安全化**：scope 参数 + 归属校验 + 确认。
5. **提取质量**：意图过滤（求助/疑问句跳过）、提取结果可见化、纠正触发加确认。
6. **scope key 规范化**：realpath + 去尾斜杠 + 向上找项目根。

### 4.2 子代理
1. 进程组击杀（对齐 gates.ts）；内置默认超时；spawn 错误透出。
2. 初始 running 反馈；中断保留部分结果；gate 期间逐条进度。
3. 输出内联上限 + 临时文件留存；`{previous}` 截断；占位符未找到报错。
4. 配置错误界面可见化（与 4.4 统一）。

### 4.3 LSP / 工具链
1. 初始化超时放宽 + 后台重试；崩溃可见化 + 文档重开。
2. web：内网逃生口（白名单配置）、bypass_cache、截断提示、search 总量截断。
3. MCP：自动重连、超时取消通知、配置错误可见化。
4. hooks：安全钩子失败可见、PostUserMessage 异步、递归防护。
5. plan：非交互超时退出、`/plan off`、放开只读调研工具。
6. cache-optimizer：官方端点白名单 + 400 自动降级。

### 4.4 配置与引导
1. 统一配置告警通道（session_start 汇总 + /doctor 集中呈现），替换全部 console.warn 静默路径。
2. guidance/doctor 路径动态化（models.json）。
3. 项目级功能被禁用时给出"如何开启"提示。
4. help/version 品牌统一。

### 4.5 界面细节
1. 列宽截断统一（复用 `truncateToWidth`）；logo 折叠协议；主题不覆盖用户选择。
2. todo 折叠判定按任务数；F7 无任务提示；页脚 git 超时退避。
3. 输入框装饰宽度对齐；DCS 序列清洗。

1. **"静默"问题最普遍**：配置错误、LSP 崩溃、钩子失效、子代理配置损坏——大量失败路径只有 `console.warn`，TUI 用户完全不可见。用户面对的是"功能悄悄不工作"，这是体验伤害最大的一种形态。

3. **健壮性缺口集中在启动与中断路径**：数据库损坏导致产品无法启动、子代理中断产生孤儿进程、LSP 冷启动锁死——这些路径平时测不到，但一旦触发就是灾难性体验。

建议按 P0 → P1 → P2 顺序推进，其中 4.1（记忆系统）与 4.4（配置可见性）两项投入产出比最高，可作为第一迭代。
